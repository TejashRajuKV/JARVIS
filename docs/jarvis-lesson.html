J.A.R.V.I.S.
a private AI assistant for your laptop

A voice and text assistant that runs on the user's own Windows computer. It understands commands in English, Telugu and Kannada, acts on the laptop, and keeps every action checked, permissioned and reversible.

1 · Problem statement

Three problems with today's assistants

Privacy

Popular assistants send every word to a company server. They cannot be trusted with personal files, and they stop working without internet.

Scattered tools

A student uses a timetable app, a notes app, a flashcard app, an attendance sheet, an editor and a PDF reader. Switching between them costs time and focus.

Unreliable AI

Chatbots can claim they did something they never did, or take actions nobody approved. There is usually no way to undo.

The project asks one question: can one assistant run locally, act on the laptop, and still be safe enough to trust?

1 · Objectives and scope

What the project set out to do

Objectives

  • Run on the user's own laptop, with an option to keep the AI fully local.
  • Understand spoken and typed commands in English, Telugu and Kannada.
  • Act on the computer: apps, system settings, files, code, dev servers.
  • Serve students and developers: study planning, attendance, notes, coding help.
  • Make every action checked, permissioned and undoable.
  • Prove it works with automated tests, not only demos.

Scope

In scope: Windows 10/11, Chrome or Edge, one user, local server.

Out of scope: macOS and Linux controls, multi-user accounts, a cloud service run by the developer, fully offline speech recognition.

1 · Solution overview

JARVIS = ears + brain + hands + mouth + guard

EarsSpeech recognition and a wake word.
→
BrainRules first, then an AI model.
→
HandsNamed tools on a Node.js server.
→
MouthText to speech in three languages.

Guard (applies to everything)

The server, not the AI, decides what is allowed. Every action has a permission tier, risky ones ask first, dangerous ones can need Windows Hello, and almost everything can be undone.

Four design rules

Rules first, AI second. About 178 commands are understood instantly by rules. Only unclear input goes to the AI.

The server decides. The AI can only propose a tool; the server validates the name, arguments and permission.

Ask before risk. Changes outside the JARVIS folder show an ALLOW / CANCEL card.

Everything reversible. Trash, earlier versions and an undo stack.

3 · nlu.js

Understanding messy human input

1. Normalize

  • Strip the wake word and fillers
  • Fix common typos and speech errors
  • Number words to digits
  • Telugu and Kannada words to English commands

2. Classify

  • Ordered pattern rules map text to an intent plus arguments
  • Fuzzy matching by edit distance for app and site names
  • Guards so statements like "I opened chrome yesterday" do not trigger actions

3. Context

Remembers the last app, file and project, so "close it" and "ask Claude to add tests" work.

4. Confidence

Low confidence goes to the AI planner instead of guessing. The paraphrase test requires zero confidently wrong answers.

3 · agent.js

How a multi-step request becomes a safe plan

IntentSplit the sentence into steps.
→
PlanningMerge, order, fill gaps from context.
→
DependenciesA step that needs an earlier one (start frontend after backend) waits for it.
→
StateCheck what is already running or open; keep it instead of redoing it.
→
PermissionsPreview risky steps; confirm once.
→
ExecutionRun in order; on failure, diagnose and propose a fix.
→
VerificationCheck the result: ✓, ✗ or ○ not checked.

Run records

Every plan gets an ID (AGT-…) and a record. "Inspect the last run" opens a card with every step, its timing, its check and what can be undone, built only from what was recorded.

Honest results

A step that cannot be verified is shown as ○ not checked, never as a false ✓. A started server gets ✓ only if it is alive and answers on its port.

Where it is built

Planning, state checks, recovery and the RETRY / CONTINUE / ROLLBACK choices are in agent.js; the server (agent-tools.js) validates every step first.

3 · agent.js · failure recovery

When a step fails, JARVIS works out why

PlanSteps, order, dependencies.
→
ExecuteRun the step.
→
FailThe server crashed.
→
UnderstandRead its real output.
→
ProposeA fix, with the reason.
→
AskALLOW / CANCEL.
→
RetryRestart once.
→
VerifyDoes it answer on its port?

Fixes (after ALLOW)

  • Missing dependencies ("Cannot find module 'express'", no node_modules) → the project's own npm install / pip install, restart.
  • Port in use by JARVIS's own leftover copy → close it, restart.
  • Generated code that fails → AI fix, shown first, max 2 tries.

Explains, doesn't fix

Any other crash gets a one-line cause instead of a bare ✗: database not reachable, missing .env setting, syntax error, permission denied. Otherwise the AI gives a likely cause, shown but never acted on.

Limits: one attempt, then report (no loops). Commands only from the project's own files. Never installs software.

3. start backend ✗ Cannot find module 'express' → ALLOW npm install + restart ✓ backend on port 5000 answering 4. start frontend ✓ answering

3 · agent.js · state awareness and transaction-like runs

Knows what is running; offers honest ways out

State awareness

Before running, the plan preview checks the current state and says what it means for each step:

Open AgriLoop in VS Code — VS Code is already open → reuse it Start the backend — already running on port 5000 → keep Close Spotify — already closed → skip Start a focus session — a 25-minute session is running → keep it

A backend JARVIS already started is kept: no second copy, no permission prompt.

When a plan fails part-way

RETRYOnly what didn't complete. Steps that worked are not repeated.
CONTINUEOnly the remaining steps that don't depend on the failed one, directly or indirectly.
ROLLBACK (n)Reverses the n changes this plan made that can be reversed, newest first: new folders to the trash, closed apps reopened, servers JARVIS started stopped again.

Transaction-like, not a full transaction. Some actions can't be undone (a sent message, an opened editor). JARVIS lists them instead of pretending.

3 · llm.js

One interface, many possible AI brains

  • Local: Ollama runs an open model (for example qwen3.5:4b) on the laptop GPU. Free, private, offline.
  • Cloud: the user's own key for OpenAI, Anthropic, Gemini, Groq, OpenRouter, DeepSeek, Mistral, Together AI or any OpenAI-compatible server. The provider is recognised from the key prefix.
  • Streaming: replies appear word by word; retries handle timeouts.
  • Tool choice: for unclear commands the AI may pick a tool, but the server validates it before anything runs.
  • Vision: screenshots go to an image-capable model for "look at my screen". They stay in memory under a single-use token that expires in two minutes.

Why the AI is kept on a leash

Language models are good at understanding and unreliable at obeying rules. So the AI only proposes. The server checks the tool name, argument schema and permission tier. A bad proposal is refused.

4 · Data and storage

Where is the chat stored?

You send a messagelogChat() in script.js adds it to chatLog.
→
TrimOnly the newest 80 messages are kept.
→
Send to serverPOST /api/state with key jarvis.chat.
→
Saved on diskServer writes ~/jarvis/.jarvis-state.json 300 ms later.

Answer

The chat is stored in one JSON file on the user's own laptop: C:\Users\<name>\jarvis\.jarvis-state.json. It is not in a cloud database and not in the browser.

Why the server, not the browser

Browser storage is per browser and per port. Keeping state on the server means every browser and port shows the same JARVIS, and the scheduler can fire reminders even when no tab is open.

Safe writing

The file is written to a .tmp copy and renamed, so a crash cannot leave a half-written file. The page loads it before any script runs (/api/state.js), and that route only answers the JARVIS page itself.

Long conversations

After 80 messages the oldest are dropped from the log, but a rolling summary (jarvis.chatSummary) is kept, so "what were we talking about?" still works the next day.

4 · Recovery

Nothing is lost by accident

Trash

Deleted files and overwritten versions go to ~/jarvis/.trash. "Undo" restores them, even from another drive.

Daily snapshots

A copy of all app data is saved to ~/jarvis/.backups at least once a day. The newest 7 daily copies are kept, plus the newest 10 safety copies taken before erase, import or restore.

Export and import

The user can export everything to a file. Secrets in the export are sealed with AES-256-GCM, with a key derived from a password using scrypt.

Erase all

"Erase all data" takes a safety snapshot first, and is guarded by Windows Hello when it is enrolled.

Undo a single action

"Undo" (or the ↶ chip) reverses the last action: deletes, file moves, volume, brightness, dark mode, opened or closed apps. The last 40 within 30 minutes.

Undo a whole task

Every action a plan makes is tagged with its run ID, so "undo that task" (or ROLLBACK on a failed plan) reverses the whole plan newest first, and says what could not be undone.

5 · Voice input (voice.js)

Speech to text

  • Uses the browser's Web Speech API (SpeechRecognition) in Chrome and Edge, in continuous mode.
  • Interim results show words live; final results arrive per phrase.
  • Language is set per request: en-IN, te-IN, kn-IN.
  • Utterance collector: joins the pieces and waits for a real quiet gap, so JARVIS answers only when the user has finished the sentence.

Speaking from far away

A gain node in the Web Audio API creates a boosted audio track, which is passed to SpeechRecognition.start(track) (Chrome 135+). Settings offer Normal, High and Max sensitivity.

5 · Wake word (wakeword.js)

"Jarvis" works even in other tabs

Problem

Browsers pause speech recognition in background tabs.

Solution

A background Windows listener (System.Speech, offline) waits for the single word. It also loads an "anything else" grammar, so random speech is rejected rather than forced into a false match.

Notification

The server pushes a wake event to the page over Server-Sent Events. The page comes forward and starts full recognition.

Conflict handling

Only one recogniser can hold the microphone. A generation counter makes late-finishing recognisers retire instead of aborting the new one.

5 · Languages (lang.js)

Telugu and Kannada support

  1. Detect the script of the input (Telugu, Kannada or Latin).
  2. Translate the command to English so the same rule engine understands it.
  3. Run the tool as usual.
  4. Translate the reply back and speak it with a Telugu or Kannada neural voice.

Words typed in English letters also work, for example volume penchu (volume up).

Design benefit

One rule engine serves three languages. Adding a language means adding words and a voice, not rewriting the commands.

5 · Study tools (study.js)

Attendance and grade calculations

Attendance bunk-o-meter (75% rule)

Attended a of t classes:

Can skip: floor(a / 0.75 − t)
Must attend in a row (if below): ceil((0.75·t − a) / 0.25)

Example: 30 of 36 attended, so 4 more classes can be skipped.

SGPA and CGPA

SGPA = Σ(credit × grade point) / Σ credits

CGPA is the credit-weighted average across semesters. Covered by 60 tests in student.test.js.

Flashcards

Spaced repetition: cards answered wrong return sooner.

Reminders

One-off, daily, weekly, monthly and yearly. The server fires them, so they work with the tab closed.

5 · Coding and automation

Coding help, routines and triggers

Run and fix code

Runs Python, JavaScript, C and C++ with a 10-second limit. On a crash, one click sends code and error to the AI to explain and fix.

Coding-AI hand-off

"Open dsa sprint in VS Code and ask Copilot to add tests." JARVIS opens the tool in the right folder and pastes the request. Supports Copilot, Claude Code, Gemini, Codex, Kiro, Trae, Antigravity, OpenCode, Qwen, Codebuff and Devin.

Dev environments

"Prepare my development environment for AgriLoop": locate the project, open VS Code, start backend and frontend, open the browser. Commands come only from the project's own package.json or entry files; ports are read from the server's own output. Failures are recovered or explained.

Learn and create

"I want to learn Python" checks the toolchain, writes and runs a real Hello World, and opens VS Code. "Create a C++ project called SmartCalc…" shows the AI's code first, compiles and runs it, and repairs it at most twice.

Routines

Named bundles of steps, for example "start my study mode".

Triggers

"When I plug in my charger, set brightness to 80." A server watcher applies cooldowns so it does not repeat.

6 · Security model

Seven layers between a request and the laptop

1. Local only

The server binds to 127.0.0.1; other machines cannot reach it.

2. Same page only

Every request is checked for JARVIS's own Host and Origin, so a random website cannot call the API (and DNS rebinding is blocked). The saved-state script also needs the browser's Sec-Fetch-Site: same-origin.

3. Tool registry

Only named tools with checked arguments exist. The AI cannot invent new ones.

4. Permission tiers

Safe actions run; risky ones preview and ask; the most dangerous can require Windows Hello.

5. Access zones

Read anywhere; ask before changing outside ~/jarvis; never touch system folders.

6. No remote approval

Phone commands and unattended routines can never approve a change.

7. Undo and panic

Trash, earlier versions and an undo stack. Saying "panic" pauses all automation.

Secrets

API keys stay on the server, masked in the page, hidden from file tools and the AI.

7 · Testing method

How the system was verified

  • Isolated server: tests start a real JARVIS with a temporary home folder and the AI pointed at a dead port. The user's own data is never touched.
  • Page self-test: headless Edge loads the real page over the DevTools Protocol. A fake speech recogniser "speaks" commands; laptop actions are replaced by recording fakes.
  • Route gate: the API suite fails if any server route is neither tested nor listed with a reason.
  • Paraphrase test: the same request said many ways. Results are correct, handed to the AI, or confidently wrong. The last must be zero.
  • Live test (opt-in): reversible checks on the real laptop, restoring volume and brightness.
  • Manual checklist: microphone, speaker, Windows Hello and phone, which need real hardware.

7 · Limitations and future work

What it does not do yet

Limitations

  • Windows is the supported platform.
  • The browser's speech recognition needs internet; only the wake word is offline.
  • A 4B local model on a 6 GB GPU is limited for long reasoning.
  • Phone commands need a JARVIS tab open on the laptop.
  • Neural voices need internet.
  • Automatic repair covers missing dependencies, a stale port and generated code; other crashes are explained, not fixed.
  • Rollback reverses only actions JARVIS knows how to undo, within 30 minutes.

Future work

  • Fully offline speech recognition (for example a Whisper model).
  • macOS and Linux controls.
  • Encrypted sync of state between devices.
  • More Indian languages.

Summary

Summary

  • JARVIS is a local assistant: a Node.js server plus a web page, on the user's own Windows laptop.
  • Commands flow Normalize → Classify → Route → Act and verify → Speak, with rules first and AI second.
