SECTION 0Start here: the pitch

Learn these three versions first. Everything else in the guide is detail behind them.

The ten-second version

Say it like this

JARVIS is a private AI assistant that runs on your own laptop. You talk or type, and it opens apps, plans your study, reads your notes and runs your code, and it asks before doing anything risky.

The one-minute version

Say it like this

Most assistants live in the cloud. They send everything to a server, they cannot touch your laptop, and they can claim they did things they did not do. JARVIS is different in three ways.

First, it runs locally: a Node.js server on your laptop plus a web page. With a local AI model, no message leaves the machine. Second, it can act: it opens apps, changes volume, reads files, runs code and even drives tools like Copilot or Claude Code. Third, it is safe: the server, not the AI, decides what is allowed, risky actions ask for permission, and almost everything can be undone.

It understands English, Telugu and Kannada, and it is tested by 29 automated test suites.

SECTION 1The problem and the goal

In one lineAssistants are cloud-based, cannot act on your laptop, and cannot always be trusted. JARVIS is local, acts, and is checked.

The three problems

Privacy

Cloud assistants send every word to a company server and stop working without internet. You cannot safely give them your personal files.

Scattered tools

A student uses a timetable app, notes app, flashcards, an attendance sheet, an editor and a PDF reader. Each switch costs focus.

Unreliable AI

A chatbot can say "done" when nothing happened, or act without asking. There is usually no undo.

Objectives

  • Run on the user's laptop, with the option to keep the AI fully local.
  • Understand voice and text in English, Telugu and Kannada.
  • Act on the computer: apps, settings, files, code, dev servers.
  • Help students and developers: study planning, attendance, notes, coding.
  • Make every action checked, permissioned and reversible.
  • Prove it works with automated tests.

Scope

In scope: Windows 10 or 11, Chrome or Edge, one user, a server on the same laptop. Out of scope: macOS and Linux controls, multiple user accounts, a cloud service run by you, and fully offline speech recognition.

Say it like this

I started from real pain points. The goal was never "a chatbot". It was an assistant you can trust with your laptop, so trust and privacy shaped every design choice.

If asked

"Is this just a ChatGPT wrapper?" No. A wrapper only sends text to a model. JARVIS has its own rule engine for 176 commands, its own tool system that acts on Windows, its own safety layer, and its own storage. The AI is one optional part.

Study features in detail

  • Attendance bunk-o-meter. Attended a of t classes. Classes you can still skip: floor(a / 0.75 − t). If below 75%, classes to attend in a row: ceil((0.75·t − a) / 0.25). Example: 30 of 36 attended, so 4 more can be skipped.
  • SGPA: Σ(credit × grade point) / Σ credits. CGPA is the credit-weighted average across semesters.
  • Flashcards use spaced repetition: cards you get wrong come back sooner.
  • Reminders can repeat, including monthly and yearly, and the server fires them even when no tab is open.
  • Viva practice asks questions by voice and grades your answers with the AI.

Coding features in detail

  • Runs .py, .js, .c and .cpp files with a 10-second limit.
  • EXPLAIN and FIX: when a program crashes, one click sends the code and error to the AI for an explanation and a fix.
  • DSA coach: gives hints first, the solution only when asked.
  • Coding-AI hand-off: "open dsa sprint in vs code and ask Copilot to add tests". JARVIS opens the tool in that folder and pastes the request. It works with Copilot, Claude Code, Gemini, Codex, Kiro, Trae, Antigravity, OpenCode, Qwen, Codebuff and Devin.
Why this design

For coding AIs, JARVIS does not write the code itself. It is a conductor, not another musician: it opens the right tool in the right place and hands over your request.

SECTION 3Architecture

In one lineA web page listens and shows; a Node.js server checks and acts; Windows, the AI and the disk do the work.

Why split page and server

A web page is not allowed to change your volume, open apps or read arbitrary files. Node.js can. So the page asks (fetch('/api/tool/…')) and the server acts. This is the classic client and server design.

Say it like this

The key idea is "rules first, AI second". A rule engine handles the common commands instantly and predictably. Only what it cannot understand goes to the AI, and even then the AI can only propose. The server decides.

If asked

"Why not send everything to the AI?" It would be slow on a laptop GPU, it can be wrong or inconsistent, and it would not work offline. Rules are instant, free and identical every time.

SECTION 4How each part works

One subsection per moving part. For each: what it is, how it works, and how to say it.

4.1 Understanding language (nlu.js)

In one lineTurns messy text into an intent plus arguments.
  1. Normalize. Remove the wake word and fillers, fix common typos and speech errors, turn number words into digits, and translate Telugu or Kannada words into English commands.
  2. Classify. Ordered pattern rules map text to an intent (SET_VOLUME) with arguments ({level: 30}). Fuzzy matching by edit distance finds "vs cod" as VS Code.
  3. Guards. "I opened chrome yesterday" is a statement, not a command, so it does not fire an action.
  4. Context. It remembers the last app, file and project, so "close it" and "ask Claude to add tests" work.
  5. Confidence. Low confidence goes to the AI planner instead of guessing. The paraphrase test requires zero confidently wrong results.
Say it like this

An intent is the "what", like set volume. Arguments are the "details", like 30. Almost every assistant turns speech into intent plus arguments. Mine does it with rules, so it is instant.

4.2 The agent (agent.js)

In one lineTurns a sentence with many jobs into a checked, permissioned plan.
IntentSplit into steps.
→
PlanningMerge, order, fill gaps.
→
DependenciesInstall before start.
→
PermissionsPreview risky steps.
→
ExecutionRun in order.
→
Verification✓, ✗ or ○ not checked.

Each plan gets an ID such as AGT-… and a run record, so "why did you do that?" is answered from evidence. If a step cannot be verified it is shown as ○ not checked, never as a false ✓. Phrases JARVIS did not understand go to a miss list, and you can TEACH it a new meaning.

Say it like this

"Open VS Code in dsa sprint, start the backend and set a timer" is three jobs. The agent splits them, checks the order, asks permission once for anything risky, runs them, and then checks each result actually happened.

4.3 The AI brain (llm.js)

In one lineOne interface to a local model or many cloud providers, always kept on a leash.
  • Local: Ollama runs an open model such as qwen3.5:4b on the GPU. Free, private, offline. An RTX 3050 with 6 GB runs it comfortably.
  • Cloud: your own key for OpenAI, Anthropic, Gemini, Groq, OpenRouter, DeepSeek, Mistral, Together AI or any OpenAI-compatible server. The provider is recognised from the key prefix (sk-ant- is Anthropic, AIza is Gemini, gsk_ is Groq).
  • Streaming: the reply appears word by word.
  • Tool choice: for unclear commands the AI may pick a tool, but the server validates the tool name, arguments and permission before anything runs.
  • Vision: "look at my screen" sends a screenshot to an image-capable model. It stays in memory under a single-use token that expires in two minutes.
Why the AI is kept on a leash

Language models are good at understanding and unreliable at following rules. So the AI proposes and the server disposes. A bad suggestion is refused, not run.

4.4 Search over your own files (rag.js)

In one lineFind the relevant passages first, then let the AI answer from only those.
ExtractPDF text per page (unpdf); Word, PowerPoint, Excel read from their zipped XML.
→
ChunkPassages tagged with file and page.
→
Keyword scoreBM25 ranking.
→
Semantic scoreOptional embeddings.
→
FuseMerge rankings, send top passages.
  • This technique is called RAG: Retrieval-Augmented Generation.
  • Keyword search is fast and exact but misses synonyms. Semantic search understands meaning ("car" matches "vehicle") but needs an embedding model.
  • Answers include page numbers, so the source can be checked.
  • A scanned PDF has no text. JARVIS detects that and says so.
  • The index lives in memory only and a file watcher rebuilds it when files change.
Say it like this

A small model cannot read a 300-page PDF at once. So I retrieve the five to ten most relevant passages and give only those to the model, with page numbers. It answers faster, makes up less, and you can verify it.

4.5 Voice input (voice.js)

In one lineThe browser turns speech into text; JARVIS waits until you have really finished.
  • Uses the browser's Web Speech API (SpeechRecognition) in continuous mode. Interim results show words live; final results arrive per phrase. The language is set per request: en-IN, te-IN or kn-IN.
  • Utterance collector. An early version answered after the first pause and cut people off. Now a collector joins the pieces and waits for a real quiet gap, so the whole sentence is sent once.
  • Mic boost. Speaking from far away showed the listening animation but no words. A gain node in the Web Audio API makes a boosted audio track that is passed to SpeechRecognition.start(track) (Chrome 135 and later). Settings: Normal, High, Max.

4.6 The wake word (wakeword.js)

In one lineA small offline Windows listener waits for "Jarvis" and wakes the page, even from another tab.
  • Problem: browsers pause speech recognition in background tabs.
  • Solution: a background listener using Windows' built-in System.Speech engine, offline. It also loads an "anything else" grammar, so random speech is rejected instead of being forced into a false "Jarvis".
  • When it hears the word, the server pushes a wake event to the page over Server-Sent Events (a one-way live stream from server to page). The page comes to the front and starts full recognition.
  • Only one recogniser can hold the microphone. A generation counter numbers each start, so a recogniser that finishes late is ignored and retired instead of aborting the new one.
Say it like this

Two engines, two jobs. A tiny offline one that only waits for one word, and a large online one that understands full sentences. Using a cheap detector to wake an expensive one is how phone assistants save battery too.

4.7 Text to speech (tts.js)

In one lineClean the reply, pick a voice, synthesize audio, play it.

Path A: browser voice

speechSynthesis with voices installed on the device. Instant and offline, but can sound robotic, and Telugu or Kannada voices are often missing.

Path B: neural voice

The server opens a WebSocket to Microsoft's online neural voice service (the one Edge's Read Aloud uses), sends the text as SSML and receives MP3 chunks. Only the reply text is sent.

LanguageJARVIS (male)FRIDAY (female)
EnglishRyan (en-GB)Neerja (en-IN)
TeluguMohan (te-IN)Shruti (te-IN)
KannadaGagan (kn-IN)Sapna (kn-IN)
  • SSML is markup that tells a voice engine what to say and how (voice, speed, pitch).
  • The service requires a security header, Sec-MS-GEC: a SHA-256 hash of the current Windows file time, rounded to 5 minutes, joined with a fixed client token. If the laptop clock is wrong, JARVIS measures the difference and corrects it.
  • FRIDAY uses Neerja because a different English voice took 5 to 15 seconds per reply and often failed in testing.
If asked

"How does text to speech work?" Say: the reply is cleaned of symbols, a voice is chosen by language and personality, then either the browser speaks it directly, or my server sends it as SSML over a WebSocket to a neural voice service and plays the MP3 that comes back.

4.8 Telugu and Kannada (lang.js)

In one lineTranslate to English, run the same rules, translate the reply back.
  1. Detect the script of the input (Telugu, Kannada or Latin).
  2. Translate the command to English so the same rule engine understands it.
  3. Run the tool as usual.
  4. Translate the reply back and speak it with a Telugu or Kannada neural voice.

Words typed in English letters also work, for example volume penchu (volume up). Online translation is optional and can be switched off in Settings.

Why this design

One rule engine serves three languages. Adding a language means adding words and a voice, not rewriting every command.

4.9 Routines, triggers and the phone

  • Routines: named bundles of steps, such as "start my study mode".
  • Triggers: "when I plug in my charger, set brightness to 80". A server watcher applies cooldowns so it does not repeat.
  • Reminders are fired by the server (scheduler.js), so they work with the tab closed.
  • Phone: reminders arrive through ntfy. Commands sent from the phone need a 6-digit TOTP code from an authenticator app (the same standard Google Authenticator uses, RFC 6238). Phone commands can never approve file changes.
  • Panic: saying "panic" pauses all automation until "resume".

  • Where skills sit in the pipeline. Skills.intercept() (skills-page.js) runs before normal command handling. While a session is active it answers directly.   • Session state. The website skill asks three questions (what, sections, style) before building. The coach gives hints first and the solution only when asked. The viva asks questions and grades each answer.

Why keep them separate

Say it like this

Most of what JARVIS does is one command answered by rules, instantly and offline. A few things, like building a website or coaching you through a problem, need a real conversation with the AI. I call those skills. They have their own steps and their own safety rules, and they sit in front of the command handler so a session can carry on across turns.

SECTION 5Where data is stored

In one lineEverything lives in one folder, ~/jarvis, on your own laptop. The chat is one JSON file.

Where is the chat stored?

→

→
Send to serverPOST /api/state, key jarvis.chat.
→
Saved to disk~/jarvis/.jarvis-state.json, 300 ms later.
Say it like this

The chat is stored in one JSON file on the user's own laptop, at C:\Users\<name>\jarvis\.jarvis-state.json. It is not in a cloud database and not in the browser. The newest 80 messages are kept, plus a rolling summary so the conversation still makes sense the next day.

Details you may be asked

  • Why the server and not the browser? Browser storage is per browser and per port. Keeping state on the server means every browser and port shows the same JARVIS, and the scheduler can fire reminders with no tab open. (Browser localStorage is only a fallback if the server snapshot fails to load.)
  • Safe writing: the server writes a .tmp copy and renames it, so a crash cannot leave a half-written file.
  • Loading: the page loads the state before any script runs, from /api/state.js. That route only answers requests from the JARVIS page itself.
  • The summary: after 80 messages the oldest are dropped from the log, but jarvis.chatSummary keeps a short rolling summary, so "what were we talking about?" still works.
  • Restoring: the page redraws the last 40 messages when it opens.

Recovery: nothing is lost by accident

Trash

Deleted files and overwritten versions go to ~/jarvis/.trash. "Undo" restores them, even across drives.

Daily snapshots

Saved to ~/jarvis/.backups at least once a day. The newest 7 daily copies are kept, plus the newest 10 safety copies taken before erase, import or restore.

Export and import

Everything can be exported to a file. Secrets in the export are sealed with AES-256-GCM, with a key derived from a password using scrypt.

Erase all

Takes a safety snapshot first, and is guarded by Windows Hello when it is enrolled.

SECTION 6Safety and security

In one lineThe server, never the AI, decides what is allowed, and almost everything can be undone.

Seven layers

1. Local only

The server binds to 127.0.0.1. Other machines cannot reach it.

2. Same page only

Requests must carry JARVIS's own Origin and Sec-Fetch-Site headers. A random website cannot call the API.

3. Tool registry

Only named tools with checked arguments exist. The AI cannot invent new ones.

4. Permission tiers

Safe actions run; risky ones preview and ask; the most dangerous can require Windows Hello.

5. Access zones

Read anywhere; ask before changing outside ~/jarvis; never touch system folders.

6. No remote approval

Phone commands and unattended routines can never approve a change.

7. Undo and panic

Trash, earlier versions and an undo stack. "Panic" pauses all automation.

Secrets

API keys stay on the server, masked in the page, and hidden from file tools and the AI.

Access zones

This is the model chosen after the "Project folders" question. Try the checker.

Home: ~/jarvis

JARVIS's own workspace. Changes need no question; undo covers them.

Laptop: elsewhere

Open and read freely. Write, rename, move, copy into and delete show ALLOW / CANCEL first.

Blocked

Windows, Program Files, ProgramData, AppData, key folders like .ssh, the Recycle Bin, and JARVIS's own config. Refused even if you click ALLOW.

What are "Project folders" for, then?

Only heavier work: preparing environments, starting backends and frontends, git, and the notes search index. They are no longer a gate for simply opening or reading things.

Say it like this

My first version only allowed a fixed list of folders, which was safe but annoying. Now JARVIS can open and read anywhere, and it asks before it changes anything outside its own folder. System folders and secrets are always blocked.

If asked

"What stops the AI from deleting my files?" The AI cannot run anything itself. It can only propose a registered tool. The server validates the request, and a delete outside the JARVIS folder shows an ALLOW / CANCEL card that only you can answer at the laptop. Deleted items go to a trash so undo works.

SECTION 8Testing

In one line29 automated suites check the commands, the server, the safety rules and the real page, without touching your data.

How it works

  • Isolated server. Tests start a real JARVIS with a temporary home folder and the AI pointed at a dead port. Your own files and settings are never used.
  • Page self-test. Headless Edge loads the real page, controlled over the Chrome DevTools Protocol. A fake speech recogniser "speaks" commands, and laptop actions are replaced by recording fakes.
  • Route gate. The API suite fails if any server route is neither tested nor listed with a reason.
  • Paraphrase test. The same request said many ways. Each result is correct, handed to the AI, or confidently wrong. The last must be zero.
  • Live test (opt-in). Reversible checks on the real laptop that restore volume and brightness.
  • Manual checklist. Microphone, speaker, Windows Hello and phone need real hardware.

SECTION 10Limits and future work

Say the limits yourself before someone finds them. It shows you understand the system.

Limitations

  • Windows is the supported platform.
  • The browser's speech recognition needs internet; only the wake word is offline.
  • A 4B local model on a 6 GB GPU is limited for long reasoning.
  • Phone commands need a JARVIS tab open on the laptop.
  • Neural voices need internet.
  • Scanned PDFs have no text to read.

Future work

  • Fully offline speech recognition, for example a Whisper model.
  • macOS and Linux controls.
  • Encrypted sync of the state file between devices.
  • More Indian languages.
